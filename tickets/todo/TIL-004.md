## Why
An empty container still takes up area, and area is the entire currency of the
board. A bucket you set up for work that isn't happening right now is a
permanent tax on the tiles that *are* asking for something.

Right now the only thing that disappears from the board is `done` (on a
cooldown). Structure never does — so the board slowly accumulates scaffolding
that has nothing in it, and the surface stops being coarse.

Generalises the hidden-when-empty behaviour proposed for the uncategorised
bucket in TIL-003 into a property any container (or board) can carry.

## Notes
A per-node flag — e.g. `hideWhenEmpty` — set by the human on a container, in
the same family as `weight` and the toolbar flag: it's a *layout* preference,
so it belongs to whoever owns structure, not to agents.

Open questions:

- What counts as "empty"? Genuinely no children, or no *visible* children
  (everything inside is `done`/hidden)? The second is more useful and more
  surprising — a container could vanish because its last task completed, and
  reappear the moment an agent flags something into it.
- Vanish, or shrink to a minimum? Disappearing structure is disorienting if
  the human is looking for a bucket they know exists. A "quiet" state (tiny,
  desaturated) may direct attention just as well without breaking the mental
  map of the board.
- Reappearing must be automatic and obvious — a hidden container that receives
  a `blocked` tile has to come back *glowing*, or the feature hides exactly the
  thing the tool exists to surface. This is the risk that decides the ticket.
- Default: off (opt-in per container), or on for containers the human never
  weighted? Off is safer; the uncategorised bucket in TIL-003 would ship with
  it on.
- Does it apply to boards too (an included board summary tile with nothing in
  it), and does an empty *board* differ from an empty container?
- Renderer + engine work, so hosted (tilemon-cloud) inherits via the npm
  package. Needs an affordance to reveal hidden containers when the human is
  restructuring — same problem `done` had, solved there with the show-done
  view; reuse that pattern rather than inventing a second one.
