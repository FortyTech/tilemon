## Why
The board doesn't keep itself up to date. Today a tile only changes when an
agent remembers to `tilemon flag`, or when the Stop hook fires `tilemon
reconcile` — and reconcile is expensive (a whole sealed `claude -p` judge per
stop), late (only at the *end* of a turn), and lossy (a session that never
stops cleanly, or a job the hook didn't cover, leaves a stale tile forever).
The result is a board that reflects what agents remembered to say, not what
they are actually doing — which is exactly the failure the tool exists to
prevent.

Note that the stale board has two independent causes, and this is the deeper
one. TIL-001 is the immediate breakage — the CLI sends `project` where the
multi-board server now wants `board`, so writes 400 and never land. Fixing that
restores self-reporting; it does not make the board update on its own.

Claude Code already maintains that state itself, for its own agent/job view.
Reading it is passive: no hook, no judge, no agent cooperation required. The
board becomes a *view over ground truth* instead of a log of self-reports.

## Notes
**The source.** `~/.claude/jobs/<job-id>/state.json`, one file per job, written
by Claude Code as the job runs. Observed fields (2026-07-30, CLI version is in
the file as `cliVersion`):

| Field | Maps to |
|---|---|
| `state` — `working` \| `blocked` \| `done` (others likely) | tile status → `in_progress` / `blocked` / `done`; `blocked` + a `needs` reads as our `waiting` |
| `name` + `nameSource` (`user` when the human named it) | tile name |
| `detail` | tile note (one-line headline) |
| `needs` | *the* attention payload — "ratify G1–G4 as one PR, or defer?" |
| `suggestedReply` | what the human could reply — a future reply-channel hook |
| `cwd` / `originCwd` / `worktreePath` / `worktreeBranch` | board routing (`dir` + `GET /api/resolve`) |
| `updatedAt` | `seen` / liveness — free, accurate, no write needed |
| `children[]` (`{id, href, kind:"pr"}`) | the outstanding-PR callout |
| `tempo`, `inFlight`, `fan[]` | live-vs-stalled, better than our TTL guess |
| `intent`, `sessionId`, `linkScanPath` | drill-down (the original ask + the transcript) |

That is close to a 1:1 mapping onto a tile. `needs` in particular is the exact
thing the board is for, already written down, in the agent's own words.

**Shape to explore.** A poller in the daemon (watch the jobs dir, debounce,
upsert via the existing `/api/status` engine path) rather than anything that
runs inside a session. Open questions:

- Undocumented internal format — it will change without warning. Needs to fail
  soft (stale board beats crashed daemon) and be version-sniffed via
  `cliVersion`. Decide up front how much we're willing to depend on it.
- Full `state` enumeration — only `working`/`blocked`/`done` seen in the wild
  so far; find the rest before mapping statuses.
- Does this *replace* `reconcile` or sit under it? Job state gives cheap,
  continuous, mechanical truth; the judge gives semantic truth (what a tile
  *means*, dedup against existing tiles). Likely: jobs drive liveness/status
  passively, reconcile stays for the semantic pass — but check whether
  reconcile earns its cost once this exists.
- Interactive (non-job) sessions aren't in `jobs/`. Does the same state exist
  for them elsewhere under `~/.claude/`, or do they keep using `flag`?
- Job identity is not tile identity: a job is one *session*, a tile is a
  *concern* that outlives it. Need a stable key (cwd + name? intent hash?) or
  the board grows a new tile every session — the noise failure mode.
- Hosted (tilemon-cloud) can't read the local filesystem, so this is a local
  daemon/CLI job that POSTs onward. Fits the migration: the daemon becomes the
  collector, hosted stays the surface.
