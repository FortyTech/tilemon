## Done when

The operator can customise the board's colours without editing code, and the choice is **theirs**
(per-viewer, client-side) — never baked into the shared board data, same category as weight and the
attention rules. Safe, considered defaults ship as-is so an untouched board looks exactly as it does
now.

Configurable surface (at least):
- **Signal-count bands** — the green / amber / red for 1 / 2 / 3+ attention signals (`SIGNAL_RGB` in
  `board.js`).
- **Status heat** — `waiting` amber, `blocked` red-pulse, `done` sage, the calm `in_progress` dot.
- **PR chip** — the purple (`#7C3AED`) and the failing-CI red. This is the request that spawned the
  ticket: "make the chips stand out" landed on purple, but the right answer is *let the operator pick*.
- Ideally fill / outline / pulse per state, with a live preview.

## Why

Colour currently carries real meaning (signal intensity, needs-you heat, liveness) but it's hard-coded
in `board.js`. Two reasons to open it up:

1. **Legibility is personal.** Colourblindness, ambient light, and monitor calibration all change what
   "stands out". A fixed palette that pops for one person mutes for another — and the whole product is
   *directing attention*, so the colours failing to pop is a direct product failure, not cosmetics.
2. **It came up live.** The PR-chip colour ("make those purple") is exactly this: a per-taste
   standout choice that shouldn't require a code change + publish + deploy each time.

This is already flagged in `SPEC.md` → *Next (not built)* → "Theming — per-status/category colours
(configurable)", including the idea of a `in_progress`→active-blue and a "quick win" marker colour.

## Notes / open questions

- **Where the palette lives:** operator-side, client-side (like `~/.tilemon/attention.md` locally and
  a per-viewer setting in hosted). Never a board-level field — a shared board must not carry one
  viewer's colours. A board-owner *default* overridable per viewer is a deferred sub-layer (same shape
  as the attention-rules deferral).
- **Mechanism:** `board.js` already reads CSS custom properties (`--tlm-*`) for some colours; the
  signal/chip colours are currently JS literals (`SIGNAL_RGB`, the `.pr` rules). Route them all
  through CSS variables with the current values as defaults, then a settings surface writes overrides.
  Keeps `board.js` a pure renderer — the host supplies the variables.
- **Frontend:** `board.js` (tokenise the literals) + `dashboard.html` (local settings UI) + a hosted
  settings surface (tilemon-cloud). Engine untouched — this is pure presentation.
- **Guardrail (the product test):** customisation must not let the board become a decorated wall.
  Defaults stay the opinionated, attention-first palette; customisation adjusts, it doesn't invite
  redecorating every tile. Ship presets (incl. a colourblind-safe one) over a raw colour-picker free-for-all.
- **Don't:** don't let per-status colour drift re-open the "is it blocked or waiting" ambiguity —
  keep the *semantics* fixed (blocked louder than waiting) even as the hues change.
